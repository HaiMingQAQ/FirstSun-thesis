## 架构与业务范围

后端使用同一个 `backend/yudao-server`，药店业务放在 `backend/yudao-module-pharmacy`，跨业务域调用既有服务。登录、角色、菜单、字典复用 `system`，文件与基础设施复用 `infra`，会员和支付分别复用 `member`、`pay`；不按开发人数拆微服务或重复实现框架能力。

下列编号来自原需求参考，用于设计追踪，不代表当前全部实现或验收通过；历史 A—F 标识只用于阅读已有模块与测试记录。

| 业务域（历史标识） | 原需求参考 | 业务范围 |
| --- | --- | --- |
| 基础资料（A） | ADM-001/004/030～034 | 门店、员工、药品分类、药品、条码及账号关联 |
| 采购（B） | ADM-002/005/006、WH-002 | 供应商、证照、采购订单、分批收货 |
| 库存（C） | ADM-003/008/009/011/012、WH-003/005/007 | 仓库货位、批次、库存流水、盘点、报损、效期 |
| POS（D） | POS-001～004/007～010、ADM-013/014/025 | 收银、销售、退货、交班与经营统计 |
| 处方与支付（E） | POS-005/007、ADM-015 | 处方登记、审核、交易关联、支付与退款记录 |
| 会员与线上订单（F） | ADM-016/017、WX-001～003/005～008 | 会员、积分、地址、购物车、本人订单及门店处理 |

表结构以初始化脚本及已执行迁移为准，框架表另计，不固定宣称系统只有 40 张表。表存在不能证明对应业务可运行；采购退货、养护温湿度、独立销毁台账、离线同步、优惠券、配送和评价等扩展仍需逐项核对实现与验证范围。

## 跨模块契约

| 服务边界 | 必须明确的信息与行为 |
| --- | --- |
| 药品及条码查询 | 药品 ID、分类、名称、规格、条码、价格、处方属性与启用状态；停用状态供调用方后端拦截。 |
| 库存查询与选批 | 门店、药品、批次、可售量、效期；按效期最早优先（FEFO），不能把预览当作占库成功。 |
| 采购收货入账 | 收货单号及来源行、药品、批号、生产/有效日期、仓库货位、数量、成本；收货状态、库存与流水在同一本地事务提交。 |
| 销售扣库及退货回补 | 稳定来源单号与行 ID、实际批次/货位分配、原出库引用、幂等键；限制累计回补，失败整体回滚。 |
| 会员积分 | 会员 ID、查询权限、业务类型及来源单号；销售与退款/退货事件可追溯且不重复记积分。 |
| 处方审核 | 处方 ID、归属、审核状态、药品匹配和审核人；未经审方不放行处方药交易，前端按钮不能代替服务端校验。 |
| 支付与退款 | 业务单号、金额单位、支付/退款状态与幂等键；药店金额为 DECIMAL 元，pay 边界以整数分转换并校验。外部支付需明确失败及补偿，不能依赖本地事务撤销渠道付款。 |
| 线上订单与销售 | 明确转销售、冻结、扣库、释放和补偿时点；不能在支付与核销时各扣一次。具体门禁与生命周期以会员/库存契约为准。 |

支付与储值需核对完整依赖，包括支付扩展、钱包流水及充值结构，不能仅凭支付状态展示宣称真实渠道已接通。演示支付应明确标识；真实支付、储值和线上履约仅在依赖补齐并联调验证后展示。

## 交付与演示证据

功能交付应包括页面、真实接口、数据持久化、权限校验、业务状态、接口说明及自测记录。至少保留正常、参数错误、权限不足、重复操作和适用的失败回滚证据，明确测试提交、环境、未测项与已知限制。

联合演示可依次展示：药品建档 → 采购收货 → 库存及流水 → 会员/线上订单 → 处方审核（若纳入处方销售）→ POS 销售、退货与交班 → 库存和积分核对。只展示已实现且验证的环节，答辩文档与实际代码一致。

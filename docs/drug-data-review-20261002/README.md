## 数据映射及增量导入约束（尚未执行）

| 来源字段 | 本地字段/处理 |
| --- | --- |
| 通用名、独立商品名 | `ph_drug.generic_name/trade_name`；品牌另存核验记录，不自动填商品名 |
| 单位强度与包装数量 | `specification` 明确完整包装；`dosage_form/unit` 按现有字典，不能仅按通用名猜 |
| 生产企业与持有人 | `manufacturer`填生产企业，持有人留批次资料；不能用持有人替换厂家 |
| 批准文号 | `approval_no`；保留原值及规范化值，不编造补齐 |
| 处方性质 | Rx：`drug_type=0,is_rx=1`；明确OTC甲：`1,0`；明确乙：`2,0`；不确定则排除 |
| 分类 | 复用租户163且药品性质匹配的分类；新分类须独立编码，不能混保健/器械 |
| 图片 | `image_url/images` 只引用已核验本地资源；出处许可保留在批次清单 |
| 说明资料、储存原文、版本 | 批次资料保存分章节事实与来源；`description/instructions_url` 须先确认内容权限及说明书转载范围；储存枚举不足以表达“密封/干燥”等，保留原文而不随意映射温度 |
| 条码 | 不必为每条造条码；仅在产品包装匹配且EAN/GS1类型确认后新增 `ph_drug_barcode`。追溯码不等于商品条码 |
| 租户、门店、ID | 租户固定163；目录不属于某个门店，407用于后续库存/业务。数据库生成新药品ID，清单记录映射，不复制任何旧ID |
| 价格 | 单独的演示价格清单及批次备注，用户确认后设置；不是来源真实市场价。样例没有填写价格 |
| 库存、批次、货位、流水 | 不由目录导入产生；单独审批库存初始化，按现有入库业务执行 |

拟用批次标识 `THESIS-DRUG-20261002-A`，最终应在实施前冻结内容哈希和清单。编码受32字符限制，批次+序号须控制长度。当前 `ph_drug` 没有独立批次字段和结构化来源字段，优先用外部增量清单记录本批每个新ID/编码/资源哈希，并在`remark/creator`标注真实系统批次身份；不新增虚构审核员工或审计历史。

全库查重包括所有租户和逻辑删除记录：`drug_code`、`cat_code`、`barcode` 的唯一索引不包含租户或删除位，旧软删除行仍会占用编码。`approval_no` 在DDL只是普通索引，但业务服务另作唯一校验；同批准文号多个包装不能直接重复新增，须先确认当前模型能否支持。药品身份按批准文号+企业+剂型+单位强度+包装核对，不按通用名一刀切。发生任何跨租户占用、同文号异规格、条码类型不明或资料不一致则停止该候选，不使用 `REPLACE` / 覆盖式 upsert。

独立脚本以后采用：目标环境守卫→全库冲突预检→本批已存在且内容完全一致则跳过→冲突则失败→事务内仅新增→记录本批ID。不得运行整库初始化/重置脚本。每次写入前重新验证数据库名称、163/407关系，任一不符立即停止。档案按待审状态新增，审核字段空；不把目录审核或处方审核伪造成已通过。线上展示须经真实品种审核和相应业务权限配置。

## 页面及业务边界发现

1. `mall-uniapp/sheep/api/pharmacy/common.js` 正确以 `isRx` 转为 `rx`，但没有保留 `description/instructionsUrl`。详情页没有对应说明书展示，Rx包装/部分详细资料目前整体隐藏，也未按审核通过状态恢复资料显示。
2. `AppDrugController` 的匿名列表/详情会转换返回 `AppDrugRespVO`，其中含 `description/instructionsUrl/imageUrl`，没有处方审核上下文的字段脱敏。前端隐藏并不能保护接口返回内容。这是代码层面的权限缺口，本轮只报告，未调用其他人的会员/处方数据，也未擅自修复。
3. `WxOrderServiceImpl` 及 `PrescriptionPurchaseService` 存在Rx下单前校验：无处方拒绝，并检查批准处方的归属、门店、有效性和可购明细等。加购物车与完成购买不是同一步。未用真实业务请求创建订单/库存/审核，不能宣称已完成运行态OTC/Rx验收。
4. 原20条中Rx线上开关关闭，新增Rx若也保持关闭，不能据小程序“看不到”判断Rx展示映射错误。不能为了展示或购买将其改为OTC。
